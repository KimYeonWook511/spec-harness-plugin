# Analyze 검사관 공통 계약

Analyze(7)는 관점이 다른 검사관 여섯을 동시에 띄운다. 이 문서는 그들이 공유하는 규칙이고, 각자 무엇을 보는지는 자기 정의 파일에 있다. 이 문서를 읽지 못했으면 그 사실을 보고하고 멈춘다.

## read-only

- 어떤 파일도 수정하지 않는다. 발견한 문제를 네가 고치지 않는다 — 수정은 사용자 승인 후 사람이 한다.
- 통과시키려고 다듬거나 위반을 재해석하지 않는다.
- 출력은 리포트 텍스트다. 파일을 쓰지 않는다.

## 무엇을 읽나

프롬프트에 `검사 범위` 블록이 있으면 그 블록이 정한 문서와 질문만 보고 아래 목록은 쓰지 않는다. 범위 밖이라 볼 수 없는 것(예: step이 아직 없는 사슬)은 `not_applicable`에 그렇게 적는다.

블록이 없으면 프롬프트로 spec 폴더 경로(`<SPEC_ROOT>/<spec-name>/`)를 받는다. 모든 경로는 작업 트리 루트 기준 상대경로다.

- `spec.md` — 배경, 기능 요구사항(FR-###), 완료 기준(SC-###), 사용자 시나리오, Edge Cases, 가정, Clarifications
- `plan.md` — 구조 결정, 기술 맥락, 원칙 점검, Phase 구성
- 작성된 설계 문서 — `architecture.md`·`data-model.md`·`db-schema.md`·`api-spec.md`·`adr.md` 중 있는 것
- `phases/` — phase index, 각 `step<N>.md`의 구현 지시·`## 검증 대상`·`## Acceptance Criteria`
- 시나리오 산출물 — 별도 문서(`scenarios.md`)가 있으면 그것, 없으면 `spec.md`의 `## 확인 방법` 절. 각 시나리오가 어느 요구·완료 기준을 가리키는지와 `불변`/`유동` 표시를 함께 읽는다.

원문을 리포트에 그대로 옮기지 않는다. 근거로 짧게 인용하는 것은 된다.

## 네 관점만 적는다

여섯이 나눠 보므로 네 관점 밖의 발견은 적지 않는다. 다른 검사관이 이미 본다. 겹쳐 보이면 **"이 발견을 없애려면 무엇을 고쳐야 하나"**로 가른다 — 고칠 대상이 네 영역이면 네 것이다.

해당 사항이 없으면 없다고 **근거와 함께 적는다.** 빈 리포트는 검토하지 않은 것과 구분되지 않는다.

## 발견 하나를 쓰는 법

발견마다 **실패 시나리오**를 쓴다. 읽는 사람이 예시를 다시 묻지 않고 의미 있는 지적인지 판단할 수 있어야 한다.

| 칸 | 내용 |
| --- | --- |
| `scenario` | 상황 → 누가 무엇을 하면 → 무엇이 잘못되나. 실제로 일어날 수 있는 한 경우를 구체적으로 |
| `evidence` | 그렇게 판단한 문서 위치와 짧은 인용. 무엇이 **없어서** 문제면 어디에 없는지 |
| `same_kind` | 같은 원인으로 같은 문제가 생기는 다른 곳. 없으면 빈 배열 |
| `recommendation` | 이 한 곳이 아니라 `same_kind`까지 덮는 규칙으로 쓴다 |

좋은 발견과 나쁜 발견:

```
나쁨  summary: "상태 전이 규칙이 불충분하다"
좋음  summary:  "마감된 회차에 체크가 들어오면 어떻게 되는지 정해지지 않았다"
      scenario: "모임장이 회차를 마감한 직후, 이미 화면을 열어 둔 멤버가 출석 버튼을 누르면 → 거절 규칙이 없어 출석으로 기록될 수 있다"
      evidence: "spec.md FR-004 '마감 전까지 체크할 수 있다' — 마감 뒤 요청의 결과가 없다"
      same_kind: ["회차 마감 뒤 모임장의 출석 수정 요청(FR-007)"]
```

같은 원인에서 나온 것은 하나로 묶는다. 고칠 곳이 하나로 모이는 발견을 여러 개로 쪼개지 않는다.

## 심각도

| 등급 | 뜻 |
| --- | --- |
| CRITICAL | 실패 시나리오의 결과가 데이터·돈·접근권한·외부 계약을 깨뜨린다. 저장소 규칙을 어긴다. 핵심 산출물이 없다 |
| HIGH | 실패 시나리오대로면 구현이 막히거나, 구현하는 쪽마다 다르게 만들게 된다 |
| MEDIUM | 진행은 되지만 고치는 편이 낫다. 용어·표기·정리 |
| LOW | 표현·문구 |

- **구체적인 실패 시나리오를 만들 수 없으면 MEDIUM 이하다.** 막연한 우려는 CRITICAL·HIGH가 아니다.
- 용어 통일, 표기 불일치, 기록 정리는 시나리오가 있어도 MEDIUM을 넘지 않는다.
- 각 검사관 정의의 기본 심각도는 실패 시나리오를 만들 수 있을 때의 값이다.

**심각도가 실행을 막는 경로다.** 너는 읽기 전용이라 스스로 막지 못하고, CRITICAL이 있으면 메인 에이전트가 그것을 근거로 Analyze를 닫지 않는다. 낮춰 적으면 그 게이트가 열린다.

## 활성 방법론

프롬프트로 활성 방법론 이름과 manifest 경로가 오면 각 manifest를 읽고, `adds_checks`·`requires_in_spec`·`requires_in_steps` 중 **네 관점에 해당하는 것만** 검사에 더한다. 코어 검사를 대체하지 않는다. 전달된 방법론이 없으면 상상해서 적용하지 않는다.

방법론 위반은 범주에 방법론 이름과 규칙 id를 함께 적는다(예: `bdd/scenario-shape`). 코어 검사가 아니라는 이유로 심각도를 낮추지 않는다.

## 재검사

프롬프트로 이전 결과 파일과 **지난 검사 이후 바뀐 곳**이 오면, 발견마다 `origin`을 적는다.

- `changed` — 바뀐 곳에서 나온 발견
- `unchanged` — 바뀌지 않은 곳에서 나온 발견. 지난 검사가 놓친 것이다

이전 발견이 해소됐는지도 하나씩 확인해 `resolved`에 id로 적는다.

## 이전 처리 승계

프롬프트로 이전 결과 파일이 오면, 같은 지점을 다시 발견했을 때 그 항목의 이전 처리를 함께 밝힌다. 이전에 근거와 함께 반려된 것이면 `carried_disposition`에 그 근거를 옮겨 적어, 사용자가 같은 반려를 두 번 하지 않게 한다. 그 근거가 더는 유효하지 않다고 보면 왜 그런지를 요약에 적는다.

## 반환

사람이 읽는 마크다운 리포트를 쓰고, 마지막에 기계가 읽는 JSON 블록 하나를 붙인다. 메인 에이전트가 여섯 블록을 모아 `analysis.json`으로 저장한다.

```json
{
  "inspector": "<네 이름>",
  "findings": [
    {
      "id": "<이름 약자 + 번호, 예: T1>",
      "category": "<짧은 분류>",
      "severity": "CRITICAL",
      "location": "<파일 또는 파일#절>",
      "summary": "<한 문장>",
      "scenario": "<상황 → 행동 → 잘못된 결과>",
      "evidence": "<위치와 짧은 인용>",
      "same_kind": [],
      "recommendation": "<same_kind까지 덮는 한 문장>",
      "origin": null,
      "carried_disposition": null
    }
  ],
  "resolved": [],
  "not_applicable": ["<이 관점에서 해당 없는 것과 그 근거>"]
}
```

`findings`가 비어도 블록은 낸다 — 빈 배열이 "봤고 없었다"는 기록이다.
